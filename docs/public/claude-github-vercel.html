Claude × GitHub × Vercel ことはじめ

3つの道具がどう協力して「システムが動き出す」までを作るか、図でわかる入門ガイド

1. まず、登場人物は3人だけ

難しく考えなくて大丈夫です。家を建てるのに「大工さん・倉庫・お店の人」がいるのと同じで、システム（Web アプリ・社内ツール・サービス等）を作って動かすにも 3 つの役割があります。

🤖

Claude ／ クロード

大工さん

あなたの指示でコードを書いてくれる AI。設計図どおりに「家（コード）」を組み立てる職人さん。

📦

GitHub ／ ギットハブ

倉庫＆履歴ノート

書いたコードを保管する場所。「いつ・誰が・何を変えたか」もすべて記録してくれる。

🌐

Vercel ／ バーセル

お店の人

倉庫からコードを受け取って、ブラウザから使える「動くシステム（Web アプリ）」として稼働させてくれる。

ポイント：あなたは「依頼する人」。3 人がバトンをつないで、システムを動く状態にしてくれます。

🤖 ところで「Claude」には3つの顔があります

同じ Claude でも、使う場所によって名前と得意分野が違います。最初は混乱しがちなので整理しておきましょう。

💬

Claude （クロード）

ふつうの会話用

claude.ai でブラウザから話しかける AI。文章作成・相談・調べもの向け。コードも書けるが「ファイルを直接編集」はできない。

⌨️

Claude Code （クロードコード）

開発者の手元 PC 用

自分の PC のターミナルにインストールして使う CLI 版。ファイルを直接編集・コマンド実行・git 操作までできる。本格的な開発向け。

☁️

Claude Code on the Web （Cowork）

クラウド版・スマホでも OK

ブラウザやスマホアプリから使えるクラウド型の Claude Code。PC に何もインストールせず、リポジトリを渡せばクラウド側で編集・push まで全部やってくれる。今このページもこれで作りました。

使い分けの目安：
  • 💬 Claude → 雑談・相談・文章書き
  • ⌨️ Claude Code → 自分の PC でガッツリ開発
  • ☁️ Cowork → 出先・スマホ・PC のない人でも開発を回したい

この流れの素敵なところは、あなたがやることは「Claude に話しかける」だけで、残りは全部 3 人が裏で自動的に走ってくれる、ということです。

⚠ ただし「人間のチェック」は必要：
Claude も間違えます。GitHub も Vercel も「言われたとおりに動く」だけで、内容の良し悪しは判断しません。
本番（main）に取り込む前に、必ず次のどれかで確認します:
  • 👀 プレビュー URL をブラウザで開いて見た目を確認
  • 🤖 CI（自動テスト）が緑になっているか確認
  • 🙋 Pull Request の差分を読んで「変なコード混じってないか」確認
「全自動で安心」ではなく「自動化されて確認に集中できる」が正しいイメージです。

3. なぜ 3 つ必要？ 役割分担の理由

もし無かったら…こうなる
Claude が無いコードを全部自分で書くことになる。時間も知識も必要。
GitHub が無いコードが自分のパソコンの中だけ。壊れたら終わり。誰とも共有できない。
Vercel が無いコードはあるけど、サーバーを自分で借りて設定しないと公開できない。

つまり 3 つ揃うと、「思いつく → 形になる → 公開される」が一直線になります。

7. つなぎ方（セットアップの全体像）

1

GitHub にアカウントを作って、リポジトリ（箱）を1つ作る

無料で OK。これが「コードの倉庫」になります。

2

Vercel にアカウントを作って、GitHub と連携する

「GitHub でログイン」を選び、さっき作ったリポジトリを Vercel に紐づけます。これで GitHub に push されると Vercel が自動で気づくようになります。

3

Claude にリポジトリを触ってもらう

Claude Code（または Cowork / Claude のウェブ版）にリポジトリを渡し、「こういうシステムを作って」と依頼。Claude がコードを書いて GitHub に push してくれます。

4

あとは自動！

push されると Vercel が検知 → ビルド → 公開 URL に反映。あなたはブラウザで結果を確認するだけ。

9. Claude Code / Cowork の使い方の基本

実際にあなたが手を動かす部分は、ほぼ「Claude にチャットで指示するだけ」です。流れはこんな感じ:

1

GitHub と接続する

Claude Code (Cowork) を起動すると、最初に「どのリポジトリを触る？」と聞かれます。GitHub アカウントを連携し、対象のリポジトリを選ぶと、Claude がそのコードを読める状態になります。

2

「セッション」を 1 つ立ち上げる

1 つの作業＝1 つのセッション。「お問い合わせフォームを追加して」と話しかけたらそれが 1 セッションです。Claude はその中で コードを読む → 書く → commit → push → PR 作成 までやってくれます。

3

結果を確認・マージ

Claude が PR を作ったら、Vercel のプレビュー URL で動作確認 → 問題なければマージ → 本番反映。

セッションは互いに完全に独立しています。A で「弊社の方針はこう」と説明しても、B では Claude はそれを知りません。毎回まっさらな状態から始まります。

イメージ：セッションは「会議室」。A 会議室で話したことは、B 会議室には伝わりません。

セッションは記憶を持ち越せませんが、リポジトリの中にメモを残しておけば次のセッションがそれを読んでくれます。よく使うのは:

  • CLAUDE.md — プロジェクト全体のルール・方針（毎セッション必ず読まれる）
  • .claude/HANDOFF.md — 「前回どこまでやった・次に何をする」の引き継ぎメモ
  • PR 説明文・コミットメッセージ — 過去の意図を残す
ポイント：「あれ、前回言ったのに…」と Claude にイラっとしたら、それは メモを残し忘れている サインです。重要なルールは CLAUDE.md、作業の続きは HANDOFF.md に書く癖をつけましょう。

💡 セッションを使い分けるコツ

こうしたいセッションをどう使う？
関連しない 2 つの作業を並行で進めたいセッション A と B を別々に立てる。互いに干渉しないので安全。
長い作業を翌日に持ち越したいセッション終了前に「HANDOFF.md に進捗を書いて」と頼む。
毎回必ず守ってほしいルールがあるCLAUDE.md に書く。全セッションが起動時に読む。
1 つの作業がこじれて方向修正したい同じセッションを続けるか、いっそ新セッションで「ゼロから違うアプローチで」と頼む。

🆕 新しいセッションはどう作る？

Cowork (Claude Code on the Web) の場合、左サイドバーの「New session」ボタンを押すだけ。リポジトリとブランチを選んで会話を始めれば、それで新セッション開始です。Claude Code (PC 版) なら、ターミナルで claude コマンドをもう 1 つ立ち上げれば別セッション。

コツ：テーマが変わったら新セッションを立てる。「フォーム追加」のあと「ロゴ変更」をするなら、新セッションのほうが Claude も混乱しません。

⚠ 同じセッションで延々作業するデメリット

起きること影響
コンテキスト（会話履歴）が膨らむ古い情報が圧縮（要約）され、細かい指示が抜け落ちることがある
前の話題が引きずられる「フォーム追加」の文脈で「ロゴ変更」を頼むと、フォーム関連のファイルを無駄に触ることがある
PR が肥大化1 PR に複数テーマが混ざってレビューしにくくなる
応答が遅くなる毎回大きな履歴を読み直すため

目安： 1 セッション＝1 PR＝1 テーマ。これを超えそうなら新セッションへ。

💥 セッションが切れる主な原因

  • 無操作タイムアウト: しばらく放置するとクラウドの作業環境（コンテナ）が回収される（Cowork の場合）
  • ブラウザを閉じた / 通信が切れた: 復帰できないことがある
  • コンテキスト上限: 履歴が長すぎると自動圧縮されるが、極端に長いと続行困難に
  • 手動で終了: タブを閉じる・New session を始めるなど
  • サービス側の不具合: 稀

🩹 セッションが切れたら何をする？

flowchart LR
    X["💥 セッション
切れた"]
    N["🆕 新セッション
を立てる"]
    R["📖 状況を読み込ませる
(下記 3 つ)"]
    G["✅ 続きから再開"]

    X ==> N ==> R ==> G

    style X fill:#fee2e2,stroke:#dc2626,stroke-width:2px
    style N fill:#e0f2fe,stroke:#0284c7,stroke-width:2px
    style R fill:#fef9c3,stroke:#ca8a04,stroke-width:3px
    style G fill:#dcfce7,stroke:#16a34a,stroke-width:2px
  1. 同じリポジトリ・同じブランチで新セッションを立てる（PR を作っていればその branch を指定）
  2. 新セッションに次を読ませる:
    • CLAUDE.md（プロジェクト全体ルール、起動時に自動で読まれる）
    • .claude/HANDOFF.md（前回の引き継ぎメモ、書いてあれば）
    • 該当の PR や直近のコミットログ（「PR #27 の続きをやって」と伝えるだけで Claude が読みに行く）
  3. 「ここまで進んだ。次は〇〇から」と一言添える
切れる前にやっておくと楽：大事な作業の節目で「HANDOFF.md に今の状況を書いて」と Claude に頼んでおく。これがセッションをまたぐ「保険」になります。

10. よくある質問

Q. お金はかかる？

個人の練習レベルなら GitHub も Vercel も無料枠で十分です。Claude は有料プランが必要になることがあります。

Q. 間違えて変なコードを push したら？

GitHub は履歴を全部覚えているので、いつでも「前の状態に戻す」ことができます。これが GitHub を使う一番のメリットです。

Q. Vercel じゃないとダメ？

同じ役割をする会社は他にもあります（Netlify, Cloudflare Pages など）。Vercel は GitHub との連携がいちばん簡単なので入門におすすめ。

Q. PR の「auto-merge（自動マージ）」がグレーアウトして使えない

GitHub の仕様で、無料プラン × 非公開（private）リポジトリの組み合わせでは auto-merge が使えません。次のいずれかで解決します:

  • リポジトリを Public にする（ただし秘密の鍵やトークンを公開しないよう要注意）
  • GitHub Pro（月 $4 程度）以上にアップグレード
  • そのまま 手動でマージ する（実用上は問題なし。Claude にマージを依頼してもOK）
個人練習なら「手動マージ」で十分です。チーム開発で CI 通過後に自動で取り込みたくなったら Pro を検討。
